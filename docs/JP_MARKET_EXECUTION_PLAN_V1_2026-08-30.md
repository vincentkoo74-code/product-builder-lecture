## 0. 계획 이전에 — 코드에서 확인한 사실 두 가지

계획을 세우기 전에 저장소를 확인했다. 두 가지가 이 계획 전체를 좌우한다.

### (1) 엔진은 이미 "원격 네트워크 동시 플레이"를 지원한다 — QR은 KR의 사용 맥락일 뿐이다

KR 카피는 "QR로 모이고, 진 사람이 벌칙!"이다. 얼핏 **한 자리에 모여야 하는 게임**처럼 보이지만, 실제 구현은 Supabase Realtime으로 방을 동기화하는 **네트워크 멀티플레이**다(rc3 하니스가 200ms~9초 전파지연·기기간 스큐를 검증해 온 바로 그 구조). 물리적 근접이 필요한 것은 **QR 입장 방식**이지 게임 엔진이 아니다.

→ **JP는 엔진 포크가 아니라 "입장 어댑터 교체"다.** QR 입장 → LINE 링크 입장. §1의 CORE/JP 경계가 그대로 지켜진다. 이것이 이 계획의 가장 중요한 전제다.

### (2) 진짜 제약은 "두 사람이 같은 순간에 접속해 있어야 한다"

게임은 동기식이다 — 공유 카운트다운, 5초 선택창, 미선택 시 자동선택. **비동기/턴제 지원은 코드에 전혀 없다**(`async_play`/`turnBased` 류 흔적 0건).

LINE으로 초대를 보내면 친구는 **몇 시간 뒤에 열 수도 있다.** 그때 방은 비어 있다. 이것이 JP 퍼널의 최대 이탈 지점이며, V1이 반드시 해결해야 할 단 하나의 신규 문제다.

**이미 준비된 것**: `ja` i18n 블록 존재(ko/ja/en 3개 로케일, `data-i18n` 205개). 일본어 UI 골격은 있다.
**전무한 것**: LIFF/LINE 연동(사실상 0), 원격 초대 플로우.

## 1. Executive Decision

**첫 공개 JP 릴리스는 "LINE 링크로 친구를 불러 지금 바로 한 판" 하나만 담는다.**

포함: LINE 진입 → 방 생성 → LINE 초대 링크 공유 → 친구 합류 → 한 판 → 결과 → 한 번 더 → 공유 → 재방문.
**Maru Tarot은 포함하지 않는다**(§4).
상업 기능은 전부 동결(§12).

근거: §14의 다섯 질문에 답하려면 변수를 최소로 둬야 한다. Tarot을 같이 넣으면 "다시 하는 이유"가 게임 자체인지 카드인지 **분리 측정이 불가능해진다.**

## 4. Maru Tarot Decision

### 결정: **OPTION A — 지금 넣지 않는다. 첫 코호트 관찰 후 즉시 후속으로 넣는다.**

| 축 | Option A (RPS만) | Option B (Tarot 동시) |
|---|---|---|
| 구현 비용 | 낮음 | 카드 8종 아트 + 획득/보관/조회 UI + 저장 스키마 → **1.5~2주 추가** |
| 출시 지연 | 없음 | 2주 |
| 리텐션 기여 | 게임 자체가 이유 | 수집 동기 추가 — 다만 **8장은 3~4판이면 절반이 찬다**, 소진 후 오히려 이탈 신호 |
| 인지 복잡도 | "친구랑 가위바위보" 한 문장 | 카드·의미·수집을 함께 설명 → 초대 카피가 무거워짐 |
| **측정 명료성** | **핵심 질문 5개에 직접 답함** | **재방문 원인이 게임인지 카드인지 분리 불가** — 이것이 결정적 |
| 법무/플랫폼 | 추가 없음 | 금전가치 없으면 추가 없음. 단 "占い" 표현은 심사 설명 필요 |
| 바이럴 | 결과 공유 | 카드 공유가 더 강할 수 있음(가설, 미검증) |

**핵심 근거**: §14는 "일본 유저가 플레이하는가 / 초대하는가 / 초대받은 친구가 실제로 들어오는가 / 다시 하는가 / 돌아오는가"를 묻는다. Tarot을 동시에 넣으면 **네 번째·다섯 번째 질문의 답이 오염된다.** Tarot은 리텐션 레버인데, 레버를 켜 둔 채로 베이스라인을 잴 수는 없다.

**단, 지금 준비해 둘 것**: 카드 8종의 **아트와 문구는 출시 전에 만들어 둔다.** 코호트 관찰 후 D+14에 즉시 켤 수 있게 — 이러면 "AB 비교"가 가능해진다(Tarot 전 코호트 vs 후 코호트).

### 포함하게 될 경우의 최소 구현
- 승자만 획득, 라운드당 1장, 중복 허용
- 저장은 `participants`가 아니라 **계정 단위 별도 테이블**(방은 휘발)
- 획득 연출은 결과 화면 **다음** 1탭 — 코어 루프(한 번 더)를 가리지 않는다
- 금전가치·쿠폰·확률형 요소 **일절 없음** (§6 원칙 + 景表法 회피)

```
DISCOVERY        X / LINE 대화 / 지인 공유
   ↓             [측정] 유입 소스별 진입
LINE ENTRY       LINE MINI App 열기 → LIFF 초기화 → 프로필
   ↓             ★이탈지점 1: 권한 동의
FIRST GAME       "친구 부르기" 단일 CTA로 방 생성
   ↓
INVITATION       LINE 대화에 초대 링크 전송
   ↓             ★이탈지점 2: 보낼 친구를 고르는 마찰
FRIEND JOINS     친구가 링크 탭 → 방 합류
   ↓             ★★이탈지점 3(최대): 초대자가 이미 나감 / 시간차
                 → [해법] 대기 화면 유지 + 합류 시 LINE 알림
MATCH            카운트다운 → 5초 선택 → 판정
   ↓
RESULT           승패 표시
   ↓
REMATCH          "もう一回" — 방 유지, 재초대 불필요  ← 최단 루프
   ↓
SHARE            결과를 LINE/X로 공유
   ↓
RETURN           D1 / D7 재방문
```

**Tarot 삽입 위치(후속 시)**: `RESULT` 다음, `REMATCH` **앞이 아니라 옆**. 결과 화면에 카드 획득 배지만 띄우고, 카드함은 별도 탭. **코어 루프를 한 탭도 늘리지 않는다.**

## 6. Japanese Positioning

한국어 카피를 직역하지 않았다. KR의 "QR로 모이고 진 사람이 벌칙"은 **오프라인 모임 전제**라 JP 원격 맥락에 맞지 않는다.

### Positioning statement
> LINEで送って、そのまま一緒にじゃんけん。

### Tagline 후보
1. **「送って、すぐ勝負。」** — 가장 짧고 행동 지향. 추천
2. 「友だちとLINEでじゃんけん。」 — 설명적·안전
3. 「いま、ひと勝負。」 — 가볍고 반복 사용에 어울림

### 친구 초대 카피 (LINE 대화에 붙는 문구)
> じゃんけんしよ！ここ押して👇

보조: `2人ならすぐ始められます`

### 합류 CTA
> **入って じゃんけん**

### 재대결 CTA
> **もう一回**

### 공유 CTA
> **結果をシェア**

### 결과 카피 (가볍게)
- 승: `勝ち！つよい🐾`
- 패: `負け…もう一回？`
- 무: `あいこ！もう一回`

**톤 원칙**: 경어체 과다·마케팅 냄새 금지. LINE 대화에 그대로 붙여도 어색하지 않은 길이(20자 이내). 이모지는 하나까지.

## 7. KPI Framework

### North-star 평가
제안된 **"활성 유저당 신규 매치 참가자 수"**는 장기 북극성으로는 **적절하다**(바이럴 계수와 직결). 다만 **출시 직후에는 N이 작아 노이즈가 크다.**

→ **북극성은 유지하되, 런치 단계 대리지표를 함께 둔다.**

| | 지표 |
|---|---|
| **North-star (장기)** | 활성 유저당 신규 매치 참가자 수 |
| **런치 대리지표 (0~30일)** | **초대 1건당 완료된 2인 매치 수** — §14 질문 2·3·4를 한 숫자로 압축 |

### Primary KPIs
1. 진입 → 게임 시작 전환율
2. 첫 게임 완료율
3. 친구 초대 발생률
4. **초대 수락률**
5. **초대 → 실제 매치 성사율** ← 최대 이탈지점(§5 ★★)
6. 재대결률
7. 공유율
8. 세션당 게임 수
9. D1 / D7 재방문

### Diagnostic KPIs
- 초대 발송 → 친구 탭까지 걸린 시간 분포 (대기 화면 설계 근거)
- 대기 화면 체류시간 및 이탈률
- 방 생성 후 상대 미합류로 종료된 비율
- 라운드 중 STALL/desync 발생률 (rc3 하드 채널의 실사용 대응)
- 로케일·기종·LINE 버전별 실패율

## 9. Soft Launch Plan

**대규모 사전 포커스그룹은 필요 없다.** 이 제품은 30초면 이해되고, 실제 초대 행동은 인터뷰로 알 수 없다.

### 1차 유저 (0~20명)
- CEO·팀의 일본 개인 네트워크 — **실재하는 관계만.** 파트너십을 만들어내지 않는다.
- 목표: **기능 검증이 아니라 "초대가 실제로 전달되고 열리는가"** 확인

### 유기적 획득 (유료광고 없이)
1. **LINE 직접 공유** — 제품 자체가 채널. 가장 중요
2. **X(일본어)** — 짧은 데모 영상 1개. "送って、すぐ勝負"
3. **소규모 커뮤니티 시딩** — 실제로 접점 있는 곳만
4. 유료광고는 **초대 수락률이 안정된 뒤에만** 검토

### 피드백 수집
- 인앱 1문항: `どうでしたか？` (3단계 + 자유입력)
- 결과 화면 하단에 상시 노출, 강제 없음
- 이탈 이벤트(`jp_waiting_exit`) 발생 유저에게는 묻지 않는다 — 이미 떠난 사람에게 묻는 것은 데이터가 아니라 소음

### 반복 주기
**주 1회 배포.** 매주 월요일 지표 리뷰 → 가설 1개 → 금요일 배포. 첫 4주는 이 리듬만 지킨다.
