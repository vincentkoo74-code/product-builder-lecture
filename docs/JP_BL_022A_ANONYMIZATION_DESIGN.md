# MARU RPS V1.0_JP — JP-BL-022A 참가자 이름 익명화 아키텍처 (설계)

2026-09-03 · CRIS · **설계/국지 테스트/보고 전용 — Tokyo 미배포, 운영 행 미변경**
정책 입력(HIKARI): `CONDITIONAL / TARGET = B_ANONYMIZE`.
법적 판단은 하지 않는다. 아래는 엔지니어링 사실과 선택지다.

## 1. 현재 이름 라이프사이클

`participants.name` 은 표시용이 아니라 **식별에도 쓰인다.** 실제 사용 지점:

| 용도 | 위치 | 성격 |
|---|---|---|
| 재입장 매칭 | `find(p => p.name === name && !p.is_host)` (3곳) | **행 선택** |
| 자기 자신 탐색 | `find(p => p.name && p.name === state.nickname)` | 행 선택 |
| 중복 감지 | `filter(p => p.name === me.name && p.id !== me.id)` | 행 선택 |
| 이탈 처리 DELETE | `.eq('room_id', …).eq('name', leaveName)` | **파괴적 write** |
| 화면 렌더 | `escapeHtml(p.name)` 다수 | 표시 |

CORE(`src/game-logic.mjs`)는 다르다. `name` 참조가 **단 1곳**이며
(`summarizeGameStats` 의 `name: p.name || ''` 통과 필드) 판정·활성집합·호스트 판정은
이름을 읽지 않는다. → **익명화는 게임 의미를 바꾸지 않는다**(테스트로 고정).

## 2. 익명값 제약 (기술적)

- **`null` 불가.** `escapeHtml` 이 `String(text)` 로 시작해 화면에 문자열 `"null"` 이 뜬다.
  null 을 쓰려면 모든 렌더 지점에 가드가 필요하다.
- **`ゲスト` 불가.** JP 기본 참가 닉네임이 `ゲスト`(`MARKET_CONFIG.defaultJoinNickname`)다.
  이탈 DELETE 가 `name` 으로 걸리므로, 익명값이 살아있는 닉네임과 겹치면
  **같은 방의 익명화된 행들이 함께 삭제될 수 있다.**
- 따라서 익명값은 **사용자가 입력할 수 없는 값**이어야 한다. 닉네임 입력은 `maxlength="10"`
  이므로 10자를 넘는 값은 UI 로 만들 수 없다 — 충돌 회피에 쓸 수 있는 성질이다.
- 거짓 신원을 암시하지 않는 편이 낫다(예: 실제 사람 이름처럼 보이는 값 금지).

> ⚠️ **선행 결함(익명화와 무관하게 이미 존재).** 같은 방에 닉네임이 같은 두 명이 있으면
> 한 명의 이탈이 **둘 다 삭제**한다. 익명화는 이 결함의 영향 범위를 넓힐 수 있다.
> 별도 항목으로 등록이 필요하다(이 슬라이스에서 고치지 않았다).

## 3. B1 — 소유권 링크

`participants` 에 `owner_uid`(또는 매핑 테이블)를 추가해 삭제 시 정확히 소유 행만 익명화.

| 항목 | 평가 |
|---|---|
| 스키마 변경 | 필요 — 컬럼 추가 + 백필 불가(기존 행은 소유자 미상) |
| 게스트 | 게스트는 세션이 없어 `owner_uid` 가 NULL — **게스트 이름은 영구 잔존**(정책 목표 미달) |
| RLS | `owner_uid` 기준 정책 추가 가능(보안상 이득) |
| 삭제 순서 | 반드시 `deleteUser` **이전**에 익명화 |
| 기존 행 | 소급 불가 |
| 프라이버시 | ⚠️ **역효과** — 지금은 존재하지 않는 `사용자 ↔ 게임이력` 영구 연결 그래프를 새로 만든다 |
| LINE 미래 | LINE 신원 모델 확정 전에 소유권 모델을 고정하게 된다(HIKARI 미확정) |
| 복잡도 | 높음 |

**핵심 모순:** 프라이버시 목적의 변경이 **재식별을 더 쉽게 만드는 구조**를 새로 도입한다.
현재 `participants` 에 auth 연결이 없다는 사실 자체가 프라이버시 자산인데 B1 은 그걸 없앤다.

## 4. B2 — 목적 구속 TTL 익명화

이름은 운영상 필요한 동안에만 존재하고, 창을 지나면 일반값으로 치환. 행은 남는다.
누가 삭제를 요청했는지 알 필요가 없다 — **게스트에게도 동일하게 적용된다.**

### 이름이 실제로 필요한 구간

| 국면 | 이름 필요? | 근거 |
|---|---|---|
| 호스트 대기 / 참가자 목록 | 예 | 참가자 식별 표시 |
| 활성 라운드 / 결과 / 재대결 | 표시만 | CORE 판정은 이름을 안 읽는다 |
| 재접속·재입장 | **예 — 행 선택에 쓰인다** | `find(p => p.name === name)` |
| deferred leave | 표시만 | `leave_after_round` 는 독립 축 |
| 버려진/stale 방 | 아니오 | — |

### 후보 창 (임의로 고르지 않았다)

| 후보 | 근거 | 위험 |
|---|---|---|
| **6시간** | 라이브 실측 방 수명 max 323분(≈5.4h)을 덮는다(p50 0.14분·p95 5.68분, 373개 방) | 앱의 24시간 재입장 목록과 어긋나 재입장 매칭이 깨질 수 있다 |
| **24시간** | 앱 자신의 재입장 창(`getRecentRoomCodes` 컷오프)과 RLS write 창이 모두 24h — 제품 의미가 일치 | 관측된 필요 시간보다 4배 이상 길다 |
| 1시간 | 최소 노출 | p95 는 넘지만 max 323분 사례를 깬다 |

**엔지니어링 권고: 24시간.** 이유는 "RLS 가 24h 라서"가 아니라, **재입장 매칭이 이름에
의존**하고 그 재입장 affordance 자체가 24시간이기 때문이다. 6시간을 고르려면 재입장
매칭을 `participantId` 기준으로 먼저 바꿔야 한다(별도 선행 작업). 최종 보존기간의
법적 타당성은 HIKARI 판단이다.

## 5. TTL 실행 메커니즘

| 항목 | 평가 |
|---|---|
| RELIABILITY | ⚠️ **free plan 은 미사용 프로젝트를 자동 일시정지**한다(JP-BL-016). 일시정지 중에는 스케줄 작업이 돌지 않아 이름이 정책 창을 넘겨 남는다 |
| IDEMPOTENCY | 가능 — `where name <> '<익명값>' and created_at < now() - INTERVAL` 는 재실행 안전 |
| FAILURE_RECOVERY | 다음 실행이 밀린 행을 함께 처리(위 조건이 자연 복구) |
| TOKYO_REGION_EXECUTION | DB 내부 실행이면 리전 이탈 없음. 외부 스케줄러면 Tokyo 외부에서 호출될 수 있다 |
| SECURITY | service_role 필요(RLS 24h 창 때문에 anon/authenticated 로는 오래된 행 수정 불가) |
| OBSERVABILITY | 실행 로그·처리 건수 기록 경로가 현재 없다 |
| DEPENDENCY_ON_PAID_FEATURES | **UNKNOWN** — 저장소에 `pg_cron`/스케줄러 사용 증거가 전혀 없다. 현 배포 계획에서의 가용성 미확인 |

후보: (a) DB 내부 스케줄(pg_cron 류) (b) 예약 실행 Edge Function (c) 외부 트리거 +
service_role 유지보수 호출. **(a)의 가용성이 확인되기 전에는 어느 것도 선택할 수 없다.**

## 6. participants SELECT 강화 (JP-PARTICIPANT-READ-HARDENING · 별도 결정)

현재 `jp_participants_select USING (true)` — 기간 제한 없는 anon 열람.

| 안 | 내용 | 게스트 플레이 영향 |
|---|---|---|
| A | 운영 시간 창 내에서만 SELECT 공개 | 창 밖 과거 방 화면이 비게 된다 |
| B | 활성/최근 방에 한정(`rooms.status`/`created_at` 기준) | 진행 중 게임 무영향, 과거 조회 제한 |
| C | 현행 유지 + TTL 익명화로 내용만 무해화 | 게임 무영향, 열거 자체는 계속 가능 |

TTL(B2)이 적용되면 **열거되는 값이 이미 익명값**이므로 C 만으로도 실질 노출은 크게 준다.
A/B 는 추가 방어다. 이 슬라이스에서 배포하지 않는다.

## 7. 기존 이력 행

Tokyo 의 기존 참가자 행은 **건드리지 않았다**. 각 안의 소급성:

- B1: 소급 불가(기존 행의 소유자를 알 수 없다).
- B2: **소급 가능** — 기준이 `created_at` 뿐이라 기존 행도 같은 규칙으로 익명화된다.
  단 1회성 대량 UPDATE 가 되므로 별도 승인·배치 크기·롤백 계획이 필요하다.

## 8. stale-room 과의 관계

**분리 권고(A).** 이름 TTL 은 "표시명 무해화", stale-room 정리는 "행 수명"으로 목적이
다르고, 결합하면 한쪽 실패가 다른 쪽을 막는다. 다만 stale-room 정리가 먼저 행을 지우면
TTL 대상이 줄어드는 순서 의존만 존재한다(무해).

## 9. LINE 미래 호환

- **B2 는 LINE 신원 모델과 무관하다** — 이름 문자열의 나이만 본다. LINE 표시명이
  닉네임으로 들어와도 같은 규칙으로 익명화된다. unlink/연동 해제/게스트→LINE 전환에
  새 분기가 필요 없다.
- **B1 은 LINE 신원 모델에 종속된다** — `owner_uid` 를 무엇으로 볼지(LINE user ID?
  Supabase uid? 연동 해제 시 소유권은?)를 HIKARI 미확정 상태에서 먼저 고정하게 된다.
